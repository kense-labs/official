把 Kense 想成操作系统更准确：进程在本地发生（Work），内核保证调度、状态与权限（OS）。模型只是可替换的执行器。

<h2 id="intent">意图</h2>

用户表达的是要完成的工作，而不是一次补全。意图会被拆成可观察的步骤：读什么、改什么、调用什么、何时等人。OS 保存的是意图与期望状态，而不是一段易失的 token 流。

<h2 id="boundary">边界</h2>

每次工具调用都发生在授权范围内：文件树、仓库、网络、密钥。Work 在本机执行时仍遵守同一套策略；OS 不会因为“在云上”就自动扩大权限。

<h2 id="state">状态</h2>

会话、工具结果、审批与定时器都是实体状态。中断后按 journal 重放，已完成步骤不再执行。这是耐久执行，而不是“再问一遍模型”。

<h2 id="publish">发布</h2>

跑通的做法可以版本化：提示、工具组合、流程与策略。个人探索留在 Work；团队复用通过 OS 发布。没有发布，就没有组织记忆。

<Callout>
Work–OS 契约是双向的：本地会话与云上流程应对齐同一身份、同一对象、同一权限语义。
</Callout>
